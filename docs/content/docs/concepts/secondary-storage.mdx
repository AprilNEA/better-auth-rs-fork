---
title: Secondary Storage
description: Session, verification, and API key persistence with an application cache.
---

Install a shared backend with `BetterAuth::secondary_storage`. `MemoryCacheAdapter` and the optional `RedisAdapter` implement `SecondaryStorage`. The same backend also serves API key configurations that select secondary storage.

```rust
use std::sync::Arc;
use better_auth::store::MemoryCacheAdapter;

config.session.store_session_in_database = Some(true);
config.verification.store_in_database = true;

let auth = BetterAuth::<AppAuthSchema>::new(config)
    .store(store)
    .secondary_storage(Arc::new(MemoryCacheAdapter::new()))
    .build()
    .await?;
```

Implement `SecondaryStorage::set_native` to receive the original `FieldValue` key, a `FieldValue` value, and an optional `f64` TTL in seconds. `FieldValue::stringify_native` retains the String or Undefined result of JSON serialization. A projected Session token can have a non-string value. TTLs can be negative or NaN when the upstream caller supplies these values. Keep these arguments intact until the backend applies its storage contract. `set` remains a convenience method for string keys, string values, and unsigned TTLs and forwards to `set_native`. An absent TTL means no expiry.

API Key, Session, User refresh, Verification, and Device cache operations call `invoke_get_native`, `invoke_set_native`, and `invoke_delete_native`. The default implementations await the existing native methods. Override these invocation methods when the backend can fail synchronously before returning a completion future. The methods receive an owned `Arc<Self>` and return `SecondaryStorageFuture`, so started work can retain backend ownership. The write method distinguishes an omitted TTL argument (`None`) from an explicit Undefined TTL (`Some(None)`). Each caller preserves its existing sequential, concurrent, and transaction behavior. Verification consumption and rate-limit counters retain their separate atomic methods.

`MemoryCacheAdapter` compares keys with JavaScript Map equality and retains native values and object identity. `get_native` distinguishes a stored Undefined from an absent entry. The string and JSON read methods reject values that their return types cannot represent. The adapter stores numeric expiration times and returns an entry only when the expiration is absent or greater than the current time. Negative and NaN TTLs therefore produce cache misses. `RedisAdapter` converts keys to JavaScript string values at the Redis encoding boundary, requires String values, and sends the supplied TTL through `SET EX`. Non-string values and Redis parameter errors propagate without changing an existing entry.

Implement `get_and_delete` as one atomic operation; a separate read and delete permits replay of verification tokens. Verification consumption calls `get_and_delete_native`. Its default bridge calls the atomic JSON method for string keys. Backends that retain native values must override this method to preserve the value and the atomic operation. Memory removes the entry while holding one lock, and Redis uses `GETDEL`. Backend errors propagate. Invalid cached JSON follows the upstream cache-miss rules described below.

### Sessions

With a secondary backend, sessions use the cache by default. Set `session.store_session_in_database` to retain database rows. A missing cache entry falls back to the database only when this setting is enabled and `preserve_session_in_database` is disabled. Malformed cached session JSON returns no session even when database fallback is enabled.

For `AuthEntity` session models, `field_name` accepts the Rust field name, its camel-case name, or its Serde serialization name. The same mapping applies to database writes, response projection and secondary-storage projection. The cache stores logical field names. Handwritten session models with storage aliases must implement `AuthSession::serialized_field_name`.

Each session token stores a session and user snapshot. `active-sessions-<userId>` stores the token list and expiration times. Listing sessions reads this index and the cached records. Updating a user through the authentication store refreshes cached user snapshots. A direct database update does not refresh the cache.

Device token redemption retains the User selected before code consumption. The endpoint creates the Session from that User's projected ID, publishes the new Session for endpoint hooks, and then writes the explicit `{user, session}` cache snapshot. That write uses the projected Session token and an unclamped expiration difference. A cache error leaves the code consumed, the Session created, and the new Session published. The endpoint does not issue session cookies.

Set `session.preserve_session_in_database` with database session storage to retain ended rows. Revocation removes the cache entry and expires live database rows. The database update also applies `updatedAt` and configured `on_update` fields. Expired rows keep their dates and receive no delete hooks. Database fallback remains disabled, so a retained row cannot restore a revoked session. Repeated revocation does not repeat delete hooks.

Session creation runs database create hooks in both storage modes. Store and hook methods return `UserView` and `SessionView`; secondary storage constructs these runtime records directly. Application models remain typed persistence mappings and do not require `Deserialize` or runtime hydration. Custom stores must implement `verify_user_with_cleanup` and invoke `VerificationSessionCleanup::revoke` only for the unverified user while holding the verification lock. The callback must complete before committing verified ownership. A cache deletion failure rolls back the database transaction so a later proof can finish cleanup. Partial cache deletions remain revoked. After hooks run after commit and propagate their original errors; session revocation has already completed. A concurrent late proof retains sessions created after successful verification.

Session creation writes the cache immediately by default, including inside a database transaction. The snapshot reads the user through the active transaction. A later rollback does not undo the cache write. Call `AuthTransaction::create_session_with_deferred_secondary` to publish after commit and after the session after hooks; Passkey registration uses this explicit mode. Rollback discards deferred writes. If a deferred cache write fails after commit, the error propagates unless database session fallback is enabled. That fallback mode logs the mirror failure and retains the committed database session, matching upstream. Immediate cache-write errors always propagate.

Session updates run before hooks before the cache write. The accumulated patch updates the cache, then the database when database session storage is enabled. An after hook receives the database result in that mode, or the cached result in cache-only mode. Missing records still reach the after hook as `None`. A cache failure prevents the database write; a later database or after-hook failure preserves the completed cache write. Updating a token keeps the original cache key and index token. Cached creation time remains unchanged, and null expiration or modification dates preserve the cached dates.

Bulk user-session revocation preserves the cache when a before hook cancels the database batch. Successful revocation queues cache cleanup after the database after hooks. That cleanup logs backend deletion errors and continues, matching upstream's explicit bulk-cleanup policy. Single-token cache deletion errors and verification's pre-commit credential cleanup errors still propagate.

### Verification values

With a secondary backend, verification values use the cache by default. Set `verification.store_in_database` to keep database rows authoritative for atomic consumption. Pure-cache consumption uses `get_and_delete`; concurrent consumers can redeem a token only once. Database consumption atomically removes the latest row and invalidates older rows with the same identifier, then removes the cached representation. Expired values are consumed but cannot authorize an operation.

Lookup can fall back from malformed or missing cached verification JSON to a database record when database storage is enabled. A database lookup also removes expired verification rows unless `verification.disable_cleanup` is enabled. This cleanup runs delete hooks. Reserving a verification value requires database storage. Duplicate exclusion requires the adapter ID policy to retain the deterministic primary key and the database to reject a duplicate insert. Memory does not enforce primary-key uniqueness, and Serial generation can allocate a different key on each reservation.

Use `VerificationStore::find_verification_value` and `update_verification_value` for native values. Both methods return `Option<FieldValue>` and are also available on `AuthTransaction`. A cache read checks the original value's truthiness, runs the upstream JSON parser once, and retains a truthy parser result without projecting its root. Date and Function roots retain their identity; custom Array mapping can return another native value. Read the fields needed by a business operation with `model_property`. Apply the operation's comparison or conversion at that point.

Cache updates spread the parsed value, apply the patch, and retain the resulting object through TTL calculation, serialization, and return. TTL calculation uses `updated.expiresAt ?? parsed.expiresAt`; a null patch remains null in the returned object. Serialization callbacks can mutate that same object or produce Undefined for `set_native`. Serialization errors occur before the cache setter. Backend errors propagate with any completed backend writes intact. Cache-only updates do not run database update hooks. With database verification storage enabled, the cache write precedes the database update and remains completed if the database update fails.

`get_verification_including_expired` and `update_verification` remain explicit `VerificationView` projections. Existing custom stores gain no required methods: the new native methods default to their typed implementations. A custom store that retains native roots must override the native methods. Atomic consumption has a separate contract: it removes the cache entry first, preserves native Object, Array, and Date roots before reading expiry, rejects other non-string roots, and spreads the accepted value only after expiry conversion. Read/update parsing and atomic consumption therefore keep separate policies.

Pure-cache storage supports lookup, update, deletion, and consumption by identifier. Database-only operations that search by value or delete by an unknown row ID return an explicit configuration error. Authentication flows use identifier-based operations.

### Identifier storage

Identifier policies apply with or without secondary storage:

```rust
use better_auth::config::{
    VerificationIdentifierConfig, VerificationIdentifierStorage,
};

config.verification.store_identifier = VerificationIdentifierConfig {
    default: VerificationIdentifierStorage::Hashed,
    overrides: vec![("public:".into(), VerificationIdentifierStorage::Plain)],
};
```

`Hashed` stores an unpadded URL-safe SHA-256 digest. `Custom` accepts an asynchronous `VerificationIdentifierHasher`. Ordered prefix overrides use the first matching prefix. Hash errors abort the operation.

Reads and atomic consumption try the transformed identifier before the original plaintext identifier to support migration. Updates and ordinary deletion affect only the transformed identifier. Pure-cache consumption removes both cached representations. Database consumption deletes rows for the representation it consumed; a separate legacy plaintext database row remains until consumed or removed. These boundaries match Better Auth 1.7.6.
